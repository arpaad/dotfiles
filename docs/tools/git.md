# Git — the config, delta, lazygit

Git itself needs no defending. What is worth explaining is the six blocks in
`.gitconfig`, because every one of them changes how you *read* changes.

Config: `git/.gitconfig` → `~/.gitconfig`

> **Change `[user]` before you commit anything.** It carries my name and email
> as shipped, and git will happily author your commits as me.

---

## The config, block by block

### `[user]` — who you are

```ini
[user]
	name = Luckyman42
	email = arpad2000@gmail.com
```

The one block you must edit. Nothing else in this file is personal.

### `[core] pager` and `[interactive] diffFilter` — delta

```ini
[core]
	pager = delta

[interactive]
	diffFilter = delta --color-only
```

Two lines, because git has two separate paths for showing a diff:

| Line | Covers |
|---|---|
| `core.pager` | `git diff`, `git show`, `git log -p` |
| `interactive.diffFilter` | the hunks shown by `git add -p` |

Set only the first and `git add -p` keeps git's raw output — which is exactly
the moment you most want a readable diff. Both lines, or neither.

**To go without delta entirely:** delete these two blocks and the `[delta]`
block. Git falls back to its own pager. Nothing else in the repo breaks.

### `[delta]` — how diffs are drawn

```ini
[delta]
	navigate = true
	line-numbers = true
```

| Setting | What it does | Why |
|---|---|---|
| `navigate = true` | `n` / `N` jump to the next/previous file in a large diff | reviewing a 30-file diff by scrolling is miserable; this makes it a per-file walk |
| `line-numbers = true` | line numbers for both sides, side by side | so you can say "line 214" to someone, and find it again in the editor |

Delta's *colours* are not here — they are generated from the shared palette
(see below).

### `[merge] conflictstyle = zdiff3` — the best single line in the file

```ini
[merge]
	conflictstyle = zdiff3
```

Git's default conflict markers show you two versions and leave you to guess
what changed:

```
<<<<<<< HEAD
timeout = 30
=======
timeout = 60
>>>>>>> feature
```

Which one is the change? You cannot tell. `zdiff3` adds the **original**:

```
<<<<<<< HEAD
timeout = 30
||||||| base
timeout = 10
=======
timeout = 60
>>>>>>> feature
```

Now it is obvious: both sides raised it, from 10, and you are picking a number
rather than reconstructing intent. The `z` is the improvement over plain
`diff3` — it hoists lines both sides changed identically out of the conflict,
so the markers wrap only the genuinely conflicting part.

This costs nothing and there is no argument against it.

### `[diff] colorMoved = default`

```ini
[diff]
	colorMoved = default
```

Colours **moved** lines differently from added and deleted ones. When you
refactor — lift a function from one file to another — a normal diff shows a
big deletion and a big addition, and you have to read both to confirm they are
the same text. With `colorMoved`, moved blocks get their own colour and you can
skip them, leaving only the lines that genuinely changed.

On a refactor-heavy diff this is the difference between reviewing it and
pretending to.

### `[include]` — the theme, last

```ini
[include]
	path = ~/.config/theme/delta.gitconfig
```

Delta's colours, generated by `scripts/04-theme.sh` from the same palette as
everything else.

**The position matters.** In git config, later wins, so this include sits at
the bottom and its styles override anything above. The `[delta]` block earlier
keeps the *behaviour* settings; this file supplies the *colour*. Splitting them
that way is what lets `04-theme.sh` regenerate colour without touching
behaviour.

The `~` path means git resolves it at read time, so it works whether or not the
`theme` package is stowed — if the file is missing, git skips a missing include
silently and you get delta's default colours.

## delta

### What it's for

Rendering git diffs.

### Why this one

Git's diff output is a 2005 design: one colour for added, one for deleted, no
syntax awareness, no word-level detail. delta adds syntax highlighting inside
the diff, word-level intra-line highlighting (so a one-character change shows
as one character, not two whole lines), side-by-side line numbers, and
navigation.

It is a drop-in pager — nothing about your git workflow changes. Alternatives:
`diff-so-fancy` (similar, less actively developed), or `git`'s own
`--word-diff` (much weaker).

### How it's themed

delta follows `$BAT_THEME` for syntax highlighting — the same variable bat
uses, set in `.zshrc` from the palette. That is *why* a Go file looks the same
in `cat` and in `git diff`: same theme variable, one source. The diff-specific
colours (added/removed backgrounds) come from the generated
`delta.gitconfig`.

## lazygit

### What it's for

A terminal UI for git: stage individual hunks, write commits, browse history,
rebase interactively, resolve conflicts.

### Why this one

The command line is good at doing a known git operation and bad at *exploring*
one. Staging four hunks out of a twelve-hunk file with `git add -p` is a
guessing game; in lazygit you see them and press space. Same for "what did this
branch actually change" and interactive rebase, which is the one git operation
whose CLI is genuinely hostile.

It does not replace the CLI — it sits beside it. Commit, push and branch are
still faster typed.

### How it's configured

`lazygit/.config/lazygit/config.yml` holds colours only, and it is
**generated** by `scripts/04-theme.sh` from the shared palette. Don't hand-edit
it; edit the palette.

Fastest way in is from inside Neovim — **`Space g g`** opens it full screen,
and quitting drops you back in the editor. See
[Neovim](neovim.md) and [the Neovim tutorial](../tutorials/neovim.md).
